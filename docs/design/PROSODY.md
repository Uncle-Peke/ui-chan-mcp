# PROSODY — 演技指導（読み方をどう決めるか）

> **ういちゃんの喋り方を変えたいときに読む。** 「どこを立てるか・どこで切るか・どう終わるか」を
> 誰がどうやって決めているかの設計と、耳で確かめて分かったことの蓄積。
> 声を*出す*手順（VoiSona の導入・認証）は [../TTS.md](../TTS.md)、
> 表情そのものの分類は [CUE_CATALOG.md](CUE_CATALOG.md)。

---

この文書は `docs/` に置く。`context/` ではない。**`context/*.md` は AI に丸ごと注入される設定**で、
ここに書いてあるのは実装の話（音素長の秒数、TSML の属性名）だから、あの子が読んでも意味がない。
AI に伝わる必要があるのは記法だけで、それは `persona/ui-chan.md` と `set_cue` のツール説明に既に入っている。

実装は `src/app/prosody.ts`（記法の翻訳と TSML 編集）と `src/app/tts.ts`（合成の経路）。

## `01` 何を解いているか — 感情を*載せる*ことと、*伝わる*ことは別

演技は3つの層に分かれる。**この分離が、この文書のいちばん大事な発見。**

| 層 | 何をするか | 手段 | 誰が持つか |
|---|---|---|---|
| **音色** | 感情を**載せる** | `style_weights`（学習済みの5スタイル） | Cue |
| **構造** | 感情を**伝える** | 強調・間・語尾・速度・長さ | セリフの書き方 ＋ アプリ |
| 内容 | 何を言うか | 言葉そのもの | AI |

`style_weights` を怒り100%に振っても、**声が怒っている状態**になるだけで、どこが要点かは伝わらない。
逆に平坦な声でも、切る場所と立てる場所が正しければ怒りは伝わる。

実際、声質のつまみ（`alp`/`huskiness`/`pitch`）を可動域の端まで振って聞き比べても
「よく分からない」で、TSML（構造）に初めて触れた瞬間に印象が変わった。足りていなかったのは
**声色ではなく読み方**だった。

> [!IMPORTANT]
> この分離には副産物がある。**リアルさ（人間らしい声質）と、演技の上手さは直交する。**
> ういちゃんは合成音声らしい声のままで、演技だけ上手くできる。だから音色の層は控えめに据え置き、
> 構造の層に投資する、という選択が成立する。

## `02` 判断基準 — 何をもって「上手い」とするか

自分の耳を信じる前に、基準を持っておく。

**上手い読みと下手な読みの差は、やっていることの*種類*ではなく*量*。**
郡史郎「ナレーションのじょうずさに関する一考察」（大阪大学）が、上手い読みと下手な読みを
音響的に比較して、フォーカス（強調）実現時の上昇量を測っている。

| | 上昇量 |
|---|---|
| 低評価の音声 | 9〜11セント |
| **高評価の音声** | **11セント以上** |
| 別の箇所（低評価 / 高評価） | 12セント / **16〜20セント** |

下手な読みも同じ場所を強調してはいる。ただ**中途半端**。上手い読みは同じことを1.5〜2倍はっきりやる。
だから迷ったときは**大きめに振る**。

聞くときのチェックリスト:

1. **どこを立てているか分かるか。** 分からないなら強調が中途半端
2. **立て方は十分大きいか**
3. **語のアクセントが壊れていないか。** 強調のつもりで型が変わっていたら、それは発音間違い
4. **間が意味に対応しているか**（息継ぎではなく、切れ目・場面転換・感情の前）
5. **語尾が「続く／終わる」を正しく伝えているか**
6. **感情と速さ・高さ・間の向きが揃っているか**（怒っているのに遅い、は齟齬）

参考にした一般則（感情音声の研究）: 高覚醒（喜び・怒り）は速く・高く・間が短く・F0レンジが広い。
低覚醒（悲しみ）はその逆で、レンジが最も狭い。**ただしこの表を合成の操作としてそのまま使うと失敗する**
（→ `07`）。

## `03` 書き方で決まるもの — 記法

**演技の数値パラメータは持たない。** AI に数値を渡すと、1回の呼び出しで「何を言うか」とは別に
「数値をいくつにするか」を考えることになり、思考時間が跳ね上がる。実際 `set_cue` にあった
`pitch`/`speed`/`volume`/`intonation` は正しく動いていたのに、ほぼ一度も使われないまま廃止した。

代わりに**文を書く行為の中に埋める**。Markdown が記法を発明せず「人がすでに打っていた書き方」を
意味に昇格させたのと同じで、日本語の表記にもとからあるものを使う。

| 記法 | 効果 | 実装 |
|---|---|---|
| `、` `…` `‥` | 一拍おく | **エンジンが既にやる**（何もしない） |
| `？` | 語尾が上がる | **エンジンが既にやる** |
| `ー` | 長音として伸びる | **エンジンが既にやる** |
| `〜` | 直前の母音を伸ばす | エンジンは**無視する**ので、音素長で伸ばす |
| `っ`（語末） | 詰まって短くなる | エンジンは**逆に長くする**ので、音素長で詰める |
| `**語**` | その語を立てる | TSML でアクセント句を切り直し、直前に一拍 |

**AI が新しく覚えるのは太字だけ。** 残りは「日本語として自然に書けば、そのとおり読まれる」。

書き分けが意味の違いになる例:

| 書き方 | 読まれ方 |
|---|---|
| `はい。` / `はーい。` | ふつうの返事 / 気の抜けた返事（長音はエンジンが処理） |
| `えっ？` / `え？` | 虚をつかれた（0.15秒に詰まる） / 聞き直した |
| `へえ？` / `へえ〜？` | 鋭い聞き返し / 引っかかっている |

> [!TIP]
> 新しい表現が欲しくなったとき、**まず「書き方で表せないか」を疑う**。
> 表せるなら辞書にもコードにも足さない。辞書は「書き方では届かない誤り」だけを持つ。

## `04` 感情から決まるもの — 導出表

Cue が宣言するのは**感情だけ**（`style_weights`）。そこから演技の数値をアプリが導く。
Cue にも行にも数値は書かない。`src/app/prosody.ts` の表が実体。

| 感情 | 抑揚 `intonation` | 話速 `speed` | `〜` の伸ばし |
|---|---|---|---|
| （宣言なし） | 1.10 | 1.00 | 0.40s |
| 悲しみ Sad | 1.15 | **0.88** | 0.50s |
| 照れ Bashful | 1.30 | 1.00 | 0.55s |
| 喜び Happy | 1.70 | **1.07** | 0.50s |
| 怒り Angry | 1.60 | 1.00 | 0.25s |

複数スタイルが混ざる Cue は**重みつき平均**（`emo_disgust` = Angry 0.3 + Sad 0.2 → 抑揚 1.32）。
スタイル名はボイスライブラリ依存なので、表に無い名前は既定値に落ちる（別のボイスに差し替えても壊れない）。

`〜` の長さが感情で変わるのは、**甘えた「ねえ〜」は長く伸び、怒った「なんで〜」は短く切れる**から。
同じ記号でも、テンションで長さが違う。

> [!WARNING]
> **検証していない値を表に入れない。** 怒りの話速は 1.00 / 1.08 / 1.18 を聞き比べて
> *差が分からなかった*ので、意図的に空にしてある。研究の一般則をそのまま埋めると、
> 「効かない補正」が積み上がってデバッグ不能になる。

## `05` 辞書 — 書き方では届かない誤りを直す

エンジンは**語の既定の読みしか選べない**。文脈で読みが変わる語は外から与えるしかない。
`ui-chan.config.json` の `tts.lexicon` がその置き場所。行ごとの演出ではなく、
**いつ誰が書いても同じように直すべき固定の誤り**だけを入れる。

| 条件 | いつ使うか | 例 |
|---|---|---|
| `hl` | 既定 | |
| `hlBeforeQuestion` | 直後が `？` | 「はあ」の既定は高→低＝**溜め息**。威嚇の「はぁ？」にならない |
| `hlInCompound` | 直後が自立語の名詞 | 複合語では前部要素が平板化する（「うい」＋「ビーム」） |
| `hlMidSentence` | 文頭でない | 「ねえ」は単体なら呼びかけ、文中の「〜だよねぇ？」は同意を求める平ら |
| `pronunciation` | 読みごと差し替え | |

優先順位は**具体的なものから**（`？` → 複合語 → 文中 → 既定）。

現在の項目:

```json
{ "word": "うい",  "hl": "hl", "hlInCompound": "lh" }
{ "word": "雨衣",  "pronunciation": "ウイ", "hl": "hl", "hlInCompound": "lh" }
{ "word": "はあ",  "hlBeforeQuestion": "lh" }
{ "word": "へえ",  "hlBeforeQuestion": "lh" }
{ "word": "ねえ",  "hlMidSentence": "ll" }
{ "word": "はい",  "hlBeforeQuestion": "lh" }
```

`hl` はモーラごとの高低（`l`=低 / `h`=高）で、**読みのモーラ数と長さを合わせる**。
2モーラ語なら取りうる型は `hl` `lh` `hh` `ll` の4つしかないので、全部聞けば必ず答えが出る。

> [!IMPORTANT]
> **辞書を増やしすぎない。** 入るのは「書いても直せないもの」だけ。
> `はーい` のように書き分けで表せるものを辞書に入れると、書き分けの自由が奪われる。

## `06` エンジンの実測 — 何をやってくれて、何をやらないか

推測しないこと。全部 `POST /text-analyses` と `POST /speech-syntheses` で測った値（田中傘 2.0.1）。

**TSML** は解析結果のマークアップ。`<word>` ごとに `hl`（モーラ単位の高低）・`chain`（アクセント句の
連結）・`pronunciation`・`is_question` を持つ。これを編集して `analyzed_text` として渡すと、
`text` の代わりに使われる。

| 測ったこと | 値 |
|---|---|
| 素の合成（`text` だけ） | 約 1005ms |
| 解析（`/text-analyses`） | 約 499ms |
| TSML 経路の合計 | 約 1501ms（**+496ms**） |
| `え？` の母音 | 0.255秒 |
| `えっ？` の母音 | **0.285秒**（促音を足すと逆に長くなる） |
| 普通の母音 | 0.08〜0.17秒 |

だから **TSML の往復は必要な行だけ**通す。`needsTsml()` が「太字・`〜`・語末の `っ`・辞書語を含むか」を
見て、どれも無ければ従来どおりの速い経路。解析結果はキャッシュするので、IdlingCue / EventCue のような
固定文では2回目以降ゼロ。解析に失敗したら `analyzed_text` を付けずに送る——
**抑揚が付かないのは劣化だが、喋らないのは故障**。

エンジンが**やってくれる**こと: 読点・三点リーダの間、`？` の語尾上げ、長音（`ー`）、アクセント型の推定。

エンジンが**やらない**こと（＝この層の存在理由）:

- **どこが要点か。** 意味の問題なので、文脈を知っている書き手にしか決められない。エンジンは全部の句を
  同じ扱いにする＝フォーカスがゼロ
- **場面転換や感情の前の間**（句読点に書かれていない）
- **語尾が「完了」か「継続」か**
- **前後の文脈**（1文ずつ独立に合成している）

TTS は平均に回帰する。外さないが、際立たない。ナレーション用途では正しいチューニングで、
**キャラクターが喋る用途で物足りない**のはそのため。

### 音素列は TSML から再現できる

`phoneme_durations` は合成に使う音素列と同じ並びで渡す必要がある。一度合成して `phonemes` を
受け取ってから投げ直すと往復が増えるが、**TSML から正確に再現できる**（9例で実測一致）。規則は2つ:

1. 各 `<word>` の `phoneme` 属性を `|`（モーラ）と `,`（音素）で割って並べる
2. 句境界と読点類で `pau`。ただし**連続する `pau` は1つ**

> [!WARNING]
> 2 を間違えると全体が1つずれて、伸ばす音素が別の場所になる。
> 読点が作る `pau` と句境界の `pau` は**同じもの**。

## `07` やってはいけないこと（耳で落第した案）

全部いちど実装して、聞いて、取り下げたもの。**理由ごと残す**——同じ罠は同じ形で戻ってくる。

### `hl`（アクセント型）を書き換えて強調する

「本気」の自然な型は `lhh`。強調のつもりで頭高 `hll` にすると、強調ではなく
**アクセントの違う別の語**に聞こえる（方言や読み間違いと同じ現象）。

アクセントは**語の身分証**で、表現の層ではない。強調は**アクセント句を切り直し、直前に一拍置く**
ことで作る。日本語の強調は音量ではなく、句の切り方で山を作ること。

### `〜` を `ー` に置換して伸ばす

長音は**独立した語**として解析され、しかも `hl="l"`（低）が付く。疑問の上げは最後のモーラで
起きるので、足した長音がそれを潰す（「言ってるー？」が上がらない）。
伸ばすのは `phoneme_durations` でやり、解析結果には触らない。

### 悲しみの `intonation` を狭める

研究には「悲しみは F0 レンジが最も狭い」とある。そのまま 0.9 にしたら、
**平坦なだけで、落ち込んで聞こえない**。

あれは*自然な悲しい発話を測った*結果であって、**すでに `Sad` スタイルで悲しくなっている声に
重ねてかける操作ではない**。二重適用で感情の signal ごと潰していた。悲しみは抑揚ではなく
**話速**（0.88）で作る。

> [!IMPORTANT]
> この失敗は一般化できる。**スタイルが既にやっていることを、上から重ねない。**
> 怒りの話速が効かなかったのも同じ理由（`Angry` スタイル自体が既にやっている）。

### `intonation` を全セリフ一律で上げる

1.6 固定にしたら、短い相槌（「ふーん。」）が大げさになった。抑揚の倍率は**短い発話ほど目立つ**。
——ただし本質は長さではなく**テンション**で、感情から導出したら解決した（→ `04`）。

### 数値パラメータを AI に渡す

→ `03`。AI にも Cue 作者にも数値を書かせない。

## `08` 新しい規則の足しかた

**必ず耳で決める。** 研究にそう書いてあるから、で入れない（→ `07` の悲しみ）。

1. **仮説を立てる。** 「この語はこう読まれるべきなのに、こう読まれている」
2. **解析結果を見る。** `POST /text-analyses` で TSML を取り、`hl` と `chain` と品詞を確認する。
   だいたいここで原因が分かる（「はあ」が高→低だった、「うい」が形容詞と解析されていた、など）
3. **候補を全部作って鳴らす。** 2モーラ語なら4通りしかない。長さなら 0.10 / 0.15 / 0.20 と刻む
4. **1つずつ聞かせて選んでもらう。** まとめて7本鳴らすと忘れる。**1語ずつ**
5. **選ばれた値だけを入れる。** 差が分からなかったものは**空のままにする**
6. **理由をコードコメントに書く。** 特に「試して落第した案」は、値そのものより重要

聞き比べは `scratchpad` に使い捨てのスクリプトを書いて、`afplay` で鳴らしている。
やっているのは「解析 → TSML を1箇所だけ変える → 合成 → 並べて再生」だけ。

## `09` 未解決

- **`〜` は行末の母音しか伸ばせない。** 文中の `〜`（「まじで〜、それは…」）は、
  行末の別の母音を伸ばしてしまう。位置を記号から辿る仕組みが要る
- **語尾の処理（`delivery`）が未実装。** 「語尾を平坦に落とす＝呆れ・詰問・完了」は効果を確認したが、
  Cue に持たせるか感情から導出するか決めていない。原則（Cue は感情だけを宣言する）に従うなら後者
- **強調の「際立たせ方の大きさ」を量的に上げる手段がない。** 句の切り直しはできるが、
  上昇量そのものは指定できない。`intonation` は行全体にかかる
- **場面転換の長い間**（`…` を長い間として扱う）が未実装
- 感動詞の辞書はまだ4語。`context/VOCABULARY.md` の口癖は感動詞が多く、ここを埋めるほど「らしさ」が出る
